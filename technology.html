Architecture

Technology

The system has a small number of parts. Status: prototype in development. The architecture is still being finalised, so this page describes the current design.

Cutaway

Look inside the building

Load-management unit

In the proposed design, each of our chargers combines a Raspberry Pi 5 single-board computer, which runs the supervisory software, with our own control board and wireless-mesh radio in one enclosure. A building-level allocator shares capacity between charging points. Where the allocator runs is not yet decided.

In short: It decides how much current each car gets.

Rationale: A widely available single-board computer keeps the load-management unit local, so decisions should work without the internet.

Charger control electronics

The control board built into our charger generates and reads the control pilot signal that talks to the vehicle, measures power for each charger and switches the charging relay. It is designed to follow the SAE J1772 and IEC 61851 control-pilot standards for AC charging.

In short: Built into our charger. It talks to the car, measures power and switches charging on and off.

Rationale: One built-in board carries the standard control signal and the per-charger meter. This gives the load-management unit the measurements it needs to adjust each charger.

Metering

Each charger measures its own energy, voltage, current and power. The building's total power is measured too and passed to the load-management unit, which shares capacity under the building limit. Meter values are reported to the charging back office over OCPP 1.6.

The required accuracy and the reporting rate are not yet decided.

In short: The system knows how much power each charger and the whole building use.

Rationale: The load-management unit can only keep the building under its limit if it can see what is drawn.

Wireless mesh

Charging points communicate over a wireless mesh. Each of our chargers has its wireless-mesh radio built in. The mesh needs no mobile plan and no building Wi-Fi. Its longer-range radio link should let it reach between floors, but range is not yet proven in a building.

In short: A wireless network in which each charger passes messages along for its neighbours.

Rationale: A mesh is intended to reach across floors and garages without new data cables, and to route around a blocked or failed node. Coverage in real garages is still to be tested.

OCPP backend link

The system connects to a charging network operator over OCPP 1.6, the Open Charge Point Protocol. It reports sessions and meter values and supports remote start and stop. Local control is designed not to depend on this link.

In short: The common protocol chargers use to report to a charging network operator.

Rationale: OCPP 1.6 is an open protocol, so the system is not tied to one operator.

Safety

Software test results alone never clear a real charging session. Simulated, bench and system-level validation are kept separate.

In short: Passing tests never counts as permission to charge a real car.

Rationale: Separate validation levels keep each claim tied to its evidence until the hardware is proven on a real installation.
